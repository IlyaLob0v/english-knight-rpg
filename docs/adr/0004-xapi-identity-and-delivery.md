# ADR 0004. xAPI: кто actor, кто пишет statement, как доставлять

Статус: принято · 2026-10-26

## Решение
- **Actor** — `account { homePage: <base IRI>, name: player_id }`. Уточнение к документу: не строим actor из LTI `iss + sub` напрямую, а связываем `(iss, sub)` с `player_id`. Так история игрока не делится на «до LMS» и «после LMS», а в LRS нет ничего, кроме псевдонима.
- **Id statement'а = id попытки** (UUID). Повторная отправка из офлайн-очереди безопасна: LRS не создаёт дубль.
- **Источник записей — клиент**: движок пишет `answered`, `passed`/`failed`, `mastered`, игровые события в свой outbox; сервер принимает их на `POST /xapi/statements`, проверяет схему и что actor совпадает с игроком сессии, и кладёт в серверный outbox для LRS. `/progress/module-result` только обновляет лучший балл и шлёт его в AGS, statement не дублирует.
- **Доставка** — at-least-once: outbox с экспоненциальной задержкой и джиттером, учётом `Retry-After`; отклонённый LRS пакет разбирается поштучно, чтобы одна битая запись не блокировала остальные; после `maxAttempts` — dead-letter для ручного разбора.
- Все свои глаголы и extensions — в одном профиле `knight-v1` (`packages/xapi/src/profile.ts`). Base IRI задаётся в конфиге и после появления данных не меняется.

## Последствия
- Балл модуля сейчас сообщает клиент; для одного игрока это приемлемо, для школы нужно пересчитывать балл на сервере по принятым `answered` — задача на неделю 5.
- Хранилища outbox, связей и баллов сейчас в памяти за интерфейсами; Postgres (сервер) и IndexedDB/Dexie (клиент) реализуют те же интерфейсы.
